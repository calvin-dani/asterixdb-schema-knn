00

Orientation

VTree answers one query — “the K vectors nearest to q” — over billions of embeddings, approximately but fast. It is a hierarchical cluster-based vector index: vectors are clustered into a trained centroid tree, and a query probes only the clusters nearest to it. Three ideas make VTree its own thing:

Hierarchical clustering
A trained tree of centroids (root → interior → leaf) routes a vector to its cluster in log time, instead of scanning a flat centroid list.
LSM, shared static tree
Writes land in memory components and flush to immutable disk components. The trained tree lives once in a shared .staticstructure; every disk component embeds its own copy so it is self-contained.
Quantized & cross-pollinated
Every vector is scalar-quantized (SQ8/SQ4) for compact storage, and replicated into up to M diverse nearby clusters so recall survives cluster boundaries.

Two layers, one dependency inversion

The code splits across the two roots of the tree. The Hyracks storage engine knows nothing about AsterixDB types; everything ADM-specific — how to read a vector, how to compute a distance, how to quantize — is injected through ~18 IVTree* interfaces and persisted on the resource so a restarted node can rebuild them.

Fig 00. Two-layer architecture & the injected contracts
The one mental model to keep

A memory component navigates the shared trained tree but writes into its own buffer cache; a disk component is self-contained (its own embedded tree copy). That split — staticBufferCache != null inside VTree — explains most of the storage code you'll read: routing reads one place, payload pages live another.

01

Vector index creation

creation pipeline · patch 3760 (+ storage 3754)

CREATE INDEX … TYPE VTREE compiles to three sequential Hyracks jobs, orchestrated by QueryTranslator#doCreateIndexImpl with a metadata transaction committed between each. The index enters the catalog PENDING_ADD_OP (invisible to queries) and is only re-added PENDING_NO_OP after Job 3 succeeds. All three job specs are built by SecondaryVectorOperationsHelper.

Precondition

The dataset must have a sample index from ANALYZE DATASET — Job 1 scans it; Job 2 needs its cardinality. Missing it fails with “Vector Index requires ANALYZE statement prior to CREATE INDEX DDL.”

The three-job runtime plan

Each job is an operator DAG. Read the edge labels — the tuple format changes shape at every hop, and those shapes are what the storage layer's sort keys and bulk-loader depend on.

Cross-job handoffs. Job 1 persists a float[6] quantization constant block — [minQ, maxQ, alpha, confidenceInterval, bits, sampleCount] — onto the resource JSON (quantiles don't compose, so the local aggregate ships raw values, not partials). Job 2 emits its centroid hierarchy leaves-first, root-last, ids assigned BFS-from-root; the storage builder relies on exactly that order to place leaves at the lowest page ids and the root at the highest. Job 3 re-reads both and produces the first self-contained disk component.

Training internals worth knowing

Quantization (OSQ): per dim, q = round((clamp(x,minQ,maxQ) − minQ)·α), one byte each; α = (2^bits−1)/(maxQ−minQ). SQ4 stores codes 0–15 one per byte (not nibble-packed). Decode is q/α + minQ — a real inverse, not a cast (a historical bug that broke dot-product ranking).

k-means: k-means‖ seeding (5 rounds, ≈2k oversample) then Lloyd's (convergence 1e-4; L2-normalize centroids for cosine). RNG is Random(trainSeed·31 + partition). Activity 1 materializes the training stream to a run file (via PartitionedUUID) because Activity 2 needs multiple passes.

Open · leaf-level drop

For K ≥ 4 the K trained leaf centroids are re-keyed to level −1 and never emitted — the tree ends up with ~√K leaves and num_clusters is not honored. Prime suspect behind recall WARNs.

The SET-allowlist quirk

None of these creation knobs is registered in the SET-allowlist — only the two query knobs (compiler.vector.kmultiplier, compiler.vector.prunedsearch) are. They work with CREATE INDEX because DDL bypasses APIFramework#validateConfig; a request that also compiles a query rejects them with “unsupported query parameter.” Keep SET + CREATE INDEX in a request of their own.

…and trainseed doesn't cover the sample

trainseed seeds the clustering RNG but not sample selection when Job 2 uses a sample scan (that seed is System.currentTimeMillis()). A fully reproducible build needs the full-scan training regime (a small dataset, or the < 10k clamp) + trainseed + a seeded ANALYZE.

02

The ANN query path

optimizer + cursors · patch 3771

The query is an ordinary ORDER BY … LIMIT k; the optimizer recognizes it and swaps a full scan for an index probe. The governing design thesis: the index proposes, the plan disposes — the original ORDER BY ann_distance and LIMIT survive, so final ordering is always exact over the returned candidates. Approximation affects recall, never ranking correctness.

the query
SELECT VALUE m.idx FROM Movie m
ORDER BY ann_distance(m.embedding, [0.1, 0.2, 0.9, 0.8], "euclidean")
LIMIT 10;

The rule — IntroduceTopKAccessMethodRule

It fires only at a plan root and recurses, pushing every ancestor onto aboveLimitOps so that when a LIMIT matches it holds the whole root→LIMIT chain — that chain is what lets it prove the projection is PK-only. Eight steps: init the subtree (ORDER's child down to DATASOURCESCAN), extract filter fields, analyze the ann_distance args, match field vs. index, choose the index (first exact metric match wins — no cost model), then transform. The pivotal decision is isProjectionPkOnly: it traces every live-out variable above the LIMIT — if all resolve to PK columns, the query never needs the record, and the index-only shape applies; otherwise lookup-and-rerank.

When cross_pollination_m > 1, a DISTINCT on the PK vars dedups replicas.

Cluster advancement is governed by NprobeClusterSelectionStrategy: nprobe = max(1, floor(window × min_probe_fraction)) over the epsilon-filtered candidate list, then an iterative DFS as an overflow valve. Search stops when minClustersProbed ≥ nprobe AND resultsCollected ≥ candidateLimit. The merge-only LSMVTreeSearchCursor is reachable in exactly two ways — inside doMerge, and in test fixtures that don't set the top-K flag.

Invariant · adjacency reconciliation

Because insert and delete route the same vector through the same immutable static structure with the same injected distance function, a delete's antimatter twin gets a bit-identical ⟨distance, PK⟩ key. In the priority-queue merge the two become adjacent (antimatter first) and cancel. Sorted data pages + sorted directories are the precondition that keeps each per-component stream key-ordered.

The spillable top-K buffer SpillableTopKBuffer

The reconciled, filtered candidate stream feeds a bounded spillable top-K buffer — a max-heap of at most candidateLimit = K × max(1, kMultiplier) best-so-far candidates, keyed on the approximate query distance dqx, over a 4-frame memory budget (DEFAULT_FRAMES_LIMIT, ≈512 KiB) that spills its worst half to sorted run files when full. It is why an ANN scan over millions of candidates runs in fixed memory.

drain() array-sorts the surviving heap ascending by dqx, then takes one of two paths: no spills → inMemoryOnly, a zero-copy walk (outputLimit = length); spilled → withMerge, a k-way merge over one in-memory source + one run-file source per spill, a min-PQ on each source's current dqx, with outputLimit = candidateLimit — this is where the K × kMultiplier cap is actually enforced when collection over-grew. The iterator's getCurrentDqx() is exactly what getCurrentDistance() surfaces to the index-only plan as $$dist.

Two things to keep straight

The ranking key is dqx — the approximate query distance d(q̃, dequantize(field 3)), both operands in quantize→dequantize space — not the stored field-0 distance-to-centroid. And the cap is enforced strictly only on the merge path: the no-spill fast path can leave slightly more than candidateLimit in memory (the “grow” case), which is harmless — the downstream ORDER + LIMIT trim exactly K.

The query's own recall/latency dials ride in ann_distance's optional 4th and 5th arguments; two session SET flags can override or augment them.

Precedence & dead flags

compiler.vector.kmultiplier and compiler.vector.prunedsearch are the only two vector knobs in the SET-allowlist — the mirror image of the creation knobs. kmultiplier > 1 silently overrides arg 5; prunedsearch is accepted but wired to nothing. And if arg 3's metric doesn't match the index, the index is skipped entirely — the query full-scans with an exact ann_distance sort, so args 4/5 have no effect.

DML & the antimatter mechanism

insert · delete · upsert

DML maintenance is spliced in by IntroduceSecondaryIndexInsertDeleteRule (the case VTREE: branches), which projects each record to [vector, include…, pk…] and threads it to an IndexInsertDeleteUpsertOperator. There is no vector-specific machinery at the algebra layer beyond field selection — the accessor, distance function and quantizer all come from the persisted resource, not the DML plan.

Insert builds a data tuple via VTreeDataTupleCreator — [distance, centroid_id, quantized_distance, quantized_embedding, pk…, include…] — and inserts it distance-sorted into the cluster's data-page chain (a right-boundary binary search keeps equal distances FIFO). Delete runs the same routing, then: if the matter twin is co-resident in the unflushed memory component it is physically removed in place; otherwise a byte-identical antimatter tuple is written (same distance, cid, PK — only bit 7 of null-flag byte 0 set) and sorted in like any insert. Upsert never reaches storage as an upsert — it's decomposed into delete+insert at the operator layer; the storage upsert path throws, kept as a tripwire.

Invariant · a delete must reconcile every replica

Because a cross-pollinated record was written into all M accepted clusters, deleteVector iterates the same findReplicaClusters(vector) set and reconciles in every one. Miss a replica and its surviving copy resurfaces in ANN results — which is why routing config-identity across insert / delete / bulk-load is load-bearing, not an optimization.

Storage-layer specification

storage engine · patches 3754 a/b

Index instance anatomy

One index instance is one directory per partition, managed by LSMVTreeFileManager. Data components are named <seqStart>_<seqEnd>_vct (flush: start == end; merge: a span). There is exactly one shared .staticstructure file and one .metadata resource JSON.

The static component is held in a dedicated field, not in diskComponents; on registration addBulkLoadedDiskComponent dispatches on the isStaticStructure flag to setStaticStructure(), which re-wires every memory component. A memory component has no interior/leaf pages at all — that is the entire point of the shared tree: it pre-creates one empty directory page per leaf centroid in its buffer cache and records centroidDirPageMap[cid − first] = vbcPageId.

The three-tier structure

Navigation resolves a query in three hops: the static structure finds the closest leaf centroid; the leaf tuple's metadata_page_ptr points at a chain of directory pages keyed by max_distance; a binary search there points at the data page whose distance range covers the record.

Fig 04. Three-tier resolution — interior level fans out to leaf clusters (c0–c9); one leaf tuple's metaPtr traced to its directory + data chains

A memory component takes a shortcut at tier 1→2: navigation still reads the shared tree, but the directory page id comes straight from centroidDirPageMap[cid − first] rather than a leaf tuple's metaPtr — prepareClusterAccess splits on component kind.

Page formats

Every page is NSM: a header at offset 0, tuples growing up, a 4-byte slot array growing down from the page end. All multi-byte numbers are big-endian. Hot fields — distance, centroid id, pointers — are written as raw untagged binary; only PK and INCLUDE columns are ADM-serialized (tag + value). That is why Job 3's external sort uses raw double/int comparators on keys {1,0}.

The antimatter bit lives in the data frame: LSMVTreeDataTupleWriter sets bit 7 (0x80) of null-flag byte 0 after the base write, so a matter and antimatter tuple are byte-identical except that one bit. The leaf frame's next_leaf is dual-purpose — with the overflow flag it means intra-cluster overflow; without it, a sibling link that makes the leaf level a scannable chain.

The level byte is not tree depth

Leaf, directory and data pages are all level 0; every interior page (any height) is level 1; the index-metadata page is −1. So isLeaf() is only meaningful for static-structure pages reached by navigation — page kind is established by pointer provenance, not self-description. A stale doc comment even transposes the data-frame field order; the authoritative source is VTreeDataTupleConstants: [distance, centroidId, qDist, qEmbed, pk…].

Flush & merge lifecycle

VTree is always a secondary index, so it never self-flushes — flushes are dataset-partition-wide, scheduled by the primary index's op tracker so component boundaries stay aligned across all indexes. Both flush and merge are page-level, bounded-memory operations that produce self-contained components.

05

Cross-pollination

special mechanism

Storing a vector only in its single closest cluster fails recall when the query's true neighbours straddle a cluster boundary, or when the closest cluster is thin. Cross-pollination replicates each record into up to M nearby, diverse clusters, so the record is found regardless of which of those clusters the query probes.

Fig 07. findReplicaClusters — epsilon window, then the SPTAG relative-neighbourhood veto

For M > 1, findCloseCentroidsLevelWiseGlobalSort gathers epsilon-windowed candidates level by level, then RngAcceptanceFilter.accept applies the relative-neighbourhood rule above — vetoing a candidate that sits too close to an already-accepted replica relative to its distance from the record. The RNG comparison is deliberately full-precision even on quantized indexes (“diversity should reflect geometric truth”). M = 1 collapses to a single greedy root-to-leaf descent — byte-identical to the legacy no-replication path.

Invariant · lock-step routing across three call sites

Bulk load, insert, and delete must compute the identical replica set for a given vector — same navigation, same RNG filter, same config. This is a correctness precondition: the original DML wrote/deleted only the closest cluster while bulk load replicated into M, so deletes leaked and cancelled nothing in the other M−1 replicas. Any future routing change must move all three sites together, and only between full rebuilds.

The k_multiplier headroom contract (deferred by design)

M replicas of a record inflate the candidate stream and each consumes a top-K slot before dedup. The query must request k_multiplier with worst-case ×M headroom, or results silently fall short of K. All replicas store identical quantized-embedding bytes → identical dqx, which is exactly what makes the ⟨distance, PK⟩ adjacency reconciliation and index-only DISTINCT dedup lossless. Anything that makes the stored embedding replica-dependent (e.g. per-cluster residual encoding) breaks both.

06

INCLUDE fields

special mechanism · storage + query

INCLUDE(year, …) lets a vector index carry a few extra scalar columns inside each entry, so a WHERE predicate on them can be evaluated during the ANN search — no primary-record fetch. It is what turns SELECT … WHERE year > 2000 ORDER BY ann_distance(…) LIMIT k into a single index probe that still returns the K best matching rows. Declared between the key list and TYPE VTREE (VTREE-only), the field names/types land in Index.VectorIndexDetails.getIncludeFieldNames().

In the entry — stored at DML time

At DML time the maintenance branch projects [vector, include…, pk…] (§03) and VTreeDataTupleCreator writes the INCLUDE bytes into the fields following the PK. They travel through insert, antimatter delete, flush and merge byte-for-byte — an antimatter twin is identical down to its INCLUDE bytes.

A given INCLUDE field's physical index is numSecondaryKeys + numPrimaryKeys + positionInIncludeList — for a quantized index, 4 + P + pos. Above: 4 + 1 + 0 = 5.

Pushed into the search — at query time

PushFilterIntoVectorSearchRule inlines a WHERE over INCLUDE fields into the vector unnest's selectCondition, allocating a fresh variable per referenced field and recording its physical index in VECTOR_FILTER_VAR_MAPPING (types in VECTOR_FILTER_VAR_TYPES). At runtime the predicate is compiled against the storage-tuple offsets through VectorIndexFilterSchema, and passesTupleFilter runs it inside LSMVTreeTopKSearchCursor — after antimatter reconciliation, before the top-K buffer insert.

That placement is the whole point (see Fig 08): a filtered-out tuple never occupies a top-K slot nor counts toward nprobe, so the buffer collects the K best year > 2000 candidates. A post-filter above the ORDER would instead silently shrink recall. It also drives index selection: chooseVectorIndex skips any index whose getIncludeFieldNames() doesn't contain every filter field — an index that can serve the ANN but not the filter is passed over. The 3771 review pass hardened the rewrite: it now bails (leaving the SELECT in place) if the rewritten predicate would reference any variable that isn't a freshly-created INCLUDE var — an unrecognized access pattern leaking the source record, or two nested INCLUDE fields colliding on a shared leaf name — rather than emit a plan whose unnest references an out-of-scope variable.

Open · index-only + WHERE on an INCLUDE field

When the projection is PK-only (the index-only shape, §07) and there's a WHERE on an INCLUDE field, the record variable is dead, so neutralizeDanglingExpressions collapses the predicate to select (missing) — every row is filtered out and the query returns zero rows, no error. Workaround: project a non-indexed field (e.g. SELECT m.id, m.title) to force the lookup-and-rerank shape, where the pushdown fires correctly.

Index-only ANN

special mechanism

When every value a query projects above the LIMIT is PK-derivable (isProjectionPkOnly), the record itself is never needed — so the whole primary B-tree lookup and the exact rerank ASSIGN can be skipped. The cursor already computed a per-candidate distance during its top-K search; the plan just needs to surface it.

Fig 09. The [pk…, D(q,x)] emission — how the distance leaves the cursor

getCurrentDistance() is a thin delegate to the drain iterator's dqx — the approximate distance d(q̃, dequantize(field 3)), both operands in quantize→dequantize space. The optimizer appends $$dist (ADOUBLE) to the unnest output, rewrites the ORDER key to reference it, and neutralizes the now-dead record ASSIGNs to MISSING. Because the emitted stream is already sorted by dqx, the surviving ORDER is a per-partition no-op and LIMIT just trims. The single semantic cost: ordering is by quantized approximation; exact ordering needs the lookup-and-rerank shape.

Open · index-only + WHERE on an INCLUDE field

The index-only rewrite neutralizes the record-based predicate to select (missing), which filters every row — a silently empty result. Workaround: project a non-indexed field to force the lookup-and-rerank shape. A NaN distance from a non-top-K (streaming) cursor is a hard IOException — the optimizer should never route index-only onto that cursor.
