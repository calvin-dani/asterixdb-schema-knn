On `gerrit/storage-wrap-up-integrate` (the branch we ship; cross-pollination is NOT on `gerrit/storage-wrap-up-refactor`), cross-pollination's M-closest replication originally lived ONLY in the bulk-load operator `VTreeBulkLoaderAndGroupingOperatorDescriptor` (used by `SecondaryVectorOperationsHelper.buildLoadingJobSpec`). Incremental DML routes through `VTree.insertVector`/`deleteVector` (memory component), which placed each record in the SINGLE closest cluster → inserts under-replicated and **deletes leaked** (one antimatter cancels only 1 of M matter copies; the survivors resurface in ANN search; query-time DistinctOperator can't help since it doesn't know about the delete).

**Fix (2026-06-29):** made `insertVector`/`deleteVector` resolve the SAME M clusters bulk-load uses and write/remove one replica per cluster. Reuses identical selection: `VTree.findCloseCentroidsLevelWiseGlobalSortFromRoot` + `RngAcceptanceFilter.accept`. New `findReplicaClusters()` + `prepareClusterAccess()` (split out of the old `findClusterAndPrepareAccess`). M=1 keeps the exact legacy single-closest path.

**Plumbing:** new `CrossPollinationConfig{m,rngFactor,epsilon}` (in `storage.am.vector.utils`, Serializable, `.LEGACY`=M1) threaded like `distanceMetric`: VTreeResourceFactoryProvider (reads `cross_pollination_m`/`rng_factor`/`epsilon` from WITH-object with the SAME defaults as the bulk-load helper — keep in lock-step or delete drifts) → LSMVTreeLocalResourceFactory → LSMVTreeLocalResource (+JSON persist/restore so it survives NC restart) → LSMVTreeUtils.createLSMTree (added overload; old signature kept for tests = LEGACY) → VTreeFactory(disk)+LSMVTree(memory) → VTree ctor.

**Correctness anchors:** static structure (centroids) is immutable + identical across components, so (vector,eps,M,rng) → deterministic same M-set at insert and delete time. Relies on the ADOPTED distance+PK keyed reconciliation (`LSMVTreeTopKSearchCursor.compare` = field-0 distance then PK; this is the correct design, NOT a bug — see [[bug-vtree-antimatter-distance-keyed-reconciliation]] which is FIXED). It works per cluster here because each replica's antimatter is stamped with field-0 = dist(x, c_i) for ITS centroid, matching the bulk-load matter copy in the same cluster (same centroid → same distance, same PK) → compare()==0 → cancels in EVERY cluster x lives in. Single-cluster delete would leak x from its other M−1 clusters (the whole point of the fix). Antimatter is inserted via `insertIntoDataPages`, which keeps the data-page chain distance-sorted — the invariant the 2026-06-28 write-side fix protects and which the k-way merge's adjacency cancellation requires.

**Verified:** hyracks am-vtree + lsm-vtree + lsm-vtree-test compile clean (offline compile/test-compile). asterix-metadata edit verified by inspection (needs user's manual hyracks install + asterixdb build).

**Test:** chose integration over a storage unit test (reuses existing infra). `integration/tests` Part-3 (insert/delete correctness) now runs with `cross_pollination_m: 3, rng_factor: 3` (config-driven: `asterixdb_client.create_vector_index` emits both WITH-keys only when M>1; `test_part3._run_target` reads them from `p3_cfg`; defaults M=1 keep parts 1/2/4 unchanged). rng_factor=1 (strict SPTAG) rarely admits >1 replica, hence 3. The leak detector is Part-3's `ann_verify` — it projects `SELECT m.idx, dist` (PK-only) so `IntroduceTopKAccessMethodRule.isProjectionPkOnly()`→ index-only plan (INDEX_ONLY_ENABLED=true, no primary BTree lookup), which surfaces any replica a broken multi-cluster delete leaves behind (a primary-lookup plan would MASK it). Caveat: only meaningful if replication actually happens — needs epsilon wide enough that ≥M leaf centroids enter the candidate list before RNG; if 0.3 proves too tight on movie, widen it. Run: `integration/tests/run_tests.py --parts 3`. See [[dfs-levelwise-conflict-bug]], [[project-vtree-quantized-only]].
