Graph-style neighbors: each leaf centroid carries a list of related-neighbor leaf centroids as direct physical pointers (page id + slot), so search can hop sideways between leaf clusters without re-descending the tree. Storage-layer design only; upstream neighbor computation and search-side traversal are out of scope.

**Docs:** consolidated in `doc-graph-leaf-neighbors/` (created 2026-06-24, mirrors doc-clusterby/ convention): `README.md` (index+status), `01-storage-design.md` (the design — moved from old `doc/graph-leaf-neighbors-design.md`, includes verified "Implementation mechanics" section), `02-engineering-details.md` (code touchpoints, tuple formats, 8-byte neighbor encoding spec, dispatch/write-context plan), `03-status-and-plan.md` (decisions log D1-D6, board, build/test cmds). Design originally written on `experiment/bottom-up-static-structure` ~2026-06-11. Implementation on `experiment/bottom-up-integrated`.

**Two-pass build (from the doc):** placement pass writes leaf pages with provisional neighbor entries (centroid-id + unresolved sentinel) + builds in-memory `cid→(page,slot)` directory; resolution pass re-reads each leaf page and overwrites provisional entries in place with real pointers, then flushes. Provisional and resolved entries are the SAME fixed byte width (the core invariant). Cloud mode: placement writes local-only, resolution uses default (local+long-term) context so long-term store sees one write per page. Crash safety via completion marker in metadata. Note: this re-introduces a second pass over leaf pages, partly reversing the "write once, never revisit" property of [[project-bottom-up-static-structure]].

**Production leaf-tuple chain:** `HierarchicalKMeansPlusPlusCentroidsOperatorDescriptor` emits `[treeLevel,centroidId,parentClusterId,embedding]` → `VTreeStaticStructureCreatorOperatorDescriptor.convertToVCTreeBuilderFormat()` reshapes to leaf `[cid,embedding,quantizedBytes]` / interior `[cid,embedding]` → `partitionLsmIndex.createBulkLoader(...,params)` → `VTreeStaticStructureBuilder.add()` (the static-structure builder IS the bulk loader when numLevels/clustersPerLevel/centroidsPerCluster params are passed; dispatched in `LSMVTreeDiskComponent.createBulkLoader`). Test producer is `VectorTestStructure.buildCentroidTuples()` which feeds NON-quantized 2-field `[cid,embedding]` leaf tuples.

**Stored leaf-tuple layout & key invariant:** `VTreeLeafFrame` reads cid@0, embedding@1, quantizedBytes@2 (hardcoded), metadataPtr via `getFieldCount()-1` (always LAST). So a new field must slot in BEFORE the metadata pointer. New quantized+neighbor leaf layout: `[cid, embedding, quantizedBytes, neighborList, metadataPtr]`.

**KEY HAZARD — field-count dispatch:** `VTreeStaticStructureBuilder.createEntryTuple` distinguishes tuple shapes by `inputFieldCount` only (2=interior or non-quant-leaf, 3=quant-leaf). Adding a neighbor field to the test's 2-field leaf would make it 3-field and collide with the legacy quant 3-field shape. So step 1 wires neighbors through the QUANTIZED production path only (release path; VTree is [[project-vtree-quantized-only]]). Tests stay 2-field/green. **Planned for step 2 (two-pass builder): switch leaf/interior dispatch to use `currentLevel` instead of field count, and adopt a canonical leaf-input contract, then add a test feeding real neighbor lists.**

**Step 2b' DONE (2026-06-24) — PIVOTED to in-builder resolution (scaffold resolved on disk), superseding resolution-during-copy:**
- **Why pivot:** cross-pollination (assign a record to multiple nearby leaf clusters) and memory-component neighbor search need a neighbor's EMBEDDING. Provisional form = centroid id only → can't reach embedding. Resolved `(page,slot)` → pin → embedding. Resolution-during-copy only resolved the disk component, leaving the SCAFFOLD provisional, so it couldn't serve those consumers. So resolution moved INTO the builder (the scaffold itself becomes resolved).
- **Cloud facts driving the design:** static structure `.staticstructure` IS cloud-uploaded (written via default context → `doSyncWrite` → local+cloud; dotfile name only excludes it from component enumeration, not upload). Cloud writer is STRICTLY sequential/append-only (`AbstractCloudIOManager.ensurePosition` THROWS on offset≠position; `ICloudWriter` writes sequentially). So you can't write provisional then re-upload resolved at the same offset. Solution: placement writes leaves LOCAL-ONLY, resolution uploads them once, in ascending page-id order — and since leaves have the lowest page ids and upload before interior/root, the cloud write order is IDENTICAL to the single-pass build (so if today works in cloud, this does). KEY user insight: in both cloud and non-cloud the first pass lands on local storage, so pass two can always `pin` pages back.
- **Light infra added:** `IOManager.localWriteOnly(ByteBuffer / ByteBuffer[])` (default delegates to `doSyncWrite`, which is local off-cloud); `AbstractCloudIOManager` overrides it to `localIoManager.syncWrite` (skip cloud); new `LocalOnlyWriteContext` in hyracks-storage-common (calls `ioManager.localWriteOnly`). storage-common already depends on control-nc and the write-context API already takes the concrete `IOManager`, so `vtree` imports ONLY storage-common — no `vtree→hyracks-cloud` coupling. ~25 lines, 3 files.
- **Write-back primitive:** the in-place modify pattern is pin → `acquireWriteLatch` → modify → `releaseWriteLatch(true)` (markDirty) → `bufferCache.flush(page)` → `unpin` (precedent: `LinkedMetaDataPageManager`). `flush`→`cleanPage`→`cleanPageLocked` writes via `DefaultBufferCacheWriteContext`→`doSyncWrite`→uploads in cloud. Cache-consistent (same frame), no confiscate/stale-cache hazard. `flush` does NOT call `compressedPageWriter.prepareWrite`, but that's fine: `.staticstructure` is NOT page-compressed (user-confirmed 2026-06-24; `VTreeResourceFactoryProvider` plumbs no compressor → VTree component files use the default uncompressed path).
- **Builder (`VTreeStaticStructureBuilder`):** `leafPlacementWriter` (LocalOnlyWriteContext) for leaf pages; `recordLeafPositions()` builds `leafDirectory` cid→{pageId,slot} + `leafPageIds` (TreeSet ascending); `resolveAndUploadLeafNeighbors()` at leaf→interior transition pins/resolves/flushes each leaf ascending; `resolveLeafPageNeighbors()` rewrites field-3 (neighbor) entries via `VTreeLeafNeighborList`. Interior/root unchanged (default writer).
- **Copy now OFFSETS, not resolves:** `VTreeBulkLoader.resolveLeafNeighborPointers(...,staticBasePageId)` offsets resolved scaffold pointers by `staticBasePageId` (provisional fallback kept); `VTreeFlushLoader.offsetLeafNeighborPointers` mirrors it for flush (implemented, untested — no merge test uses quantized 5-field leaves).
- **LSM disk components are immutable** — there's no pre-existing "modify a disk page + re-upload" path; this resolution is part of BUILDING the not-yet-finalized component, which is why it's legitimate.
- Tests: `LSMVTreeLeafNeighborTest` (resolved + empty-list) green; full lsm-vtree suite `19 run, 0 fail`. **Cloud-mode (`cc-cloud-storage.conf`) NOT yet verified on a real deployment** (reasoning sound, but unrun).

**(Superseded) Step 2b — resolution via resolution-during-copy (NOT the doc's in-builder two-pass):**
- **Architecture pivot (supersedes design doc's two-pass + LocalOnlyWriteContext):** neighbors are resolved in `VTreeBulkLoader.end()` DURING the static-structure copy, not in the builder. The builder only places PROVISIONAL neighbors (2a). `end()` already confiscates each static page, copies content, and offsets pointers with uniform `newPageId = staticBasePageId + oldPageId`, writing each page once. Added: build `cid->(finalPageId, slot)` directory while copying leaf pages, then `resolveLeafNeighborPointers()` rewrites each leaf's neighbor entries (field index 3, a length-prefixed ByteArray) in place via `VTreeLeafNeighborList` + `ByteArrayPointable.getContentLength/getNumberBytesToStoreMeta`, before the single write.
- **Why this beats the doc's plan:** copy writes each final page exactly once → cloud append-only safe with NO re-upload → **no `LocalOnlyWriteContext` / `localWriter(ByteBuffer[])` needed**. Also `hyracks-storage-am-vtree` has NO `hyracks-cloud` dependency, so an in-builder cloud-aware context was unreachable anyway. Confiscation stays bounded (copy already holds only the small static-page set). Unifies former 2b+2c.
- Defensive `!isResolved` guard (skip entries whose 2nd int != SENTINEL) so an already-resolved page id is never misread as a centroid id. Correct because the static-structure source is always the canonical 0-based provisional copy (same assumption the existing child/next-leaf offsetting relies on).

**Verified storage/cloud write mechanics (2026-06-24) — the foundation for the two-pass build's cloud/non-cloud compatibility:**
- Buffer cache writes a page via an `IBufferCacheWriteContext` (two `write` overloads taking the `IOManager`). Cloud mode IOManager = `AbstractCloudIOManager` (asterix-cloud) with: `doSyncWrite` = local THEN `cloudWrite` (BOTH stores); `localWriter` = local only; `cloudWrite` = cloud only. Non-cloud IOManager: all paths are plain local `doSyncWrite`.
- Existing contexts: `DefaultBufferCacheWriteContext` (→doSyncWrite→both), `DefaultCloudOnlyWriteContext` (→cloudWrite). Need a NEW `LocalOnlyWriteContext`: `instanceof ICloudIOManager ? localWriter(...) : doSyncWrite(...)`.
- `ICloudIOManager.localWriter` only has the single-`ByteBuffer` overload; uncompressed page write uses the `ByteBuffer[]` overload (`BufferedFileHandle` writes header+page array). So ALSO add `localWriter(IFileHandle,long,ByteBuffer[])` to ICloudIOManager/AbstractCloudIOManager (= `localIoManager.doSyncWrite(fHandle,offset,dataArray)`), mirroring `cloudWrite(ByteBuffer[])`.
- **PIVOTAL: cloud upload happens ONLY inside a write call (doSyncWrite/cloudWrite). `force()`/`sync()` route to `localIoManager.sync(...)` = LOCAL ONLY in cloud mode.** So the resolution pass canNOT "modify pinned page + force" to publish final bytes to cloud — it must re-issue a real write through `DefaultBufferCacheWriteContext`.
- Confiscation memory bound: current builder already holds ≤1 page — `FIFOLocalWriter.write()` calls `bufferCache.returnPage()` in finally, returning the frame right after each write. Placement keeps this (just swap leaf-level FIFO writer to LocalOnly context; interior/root stay Default). Resolution = pin(dpid) to read provisional page from local disk → copy bytes into a fresh `confiscatePage(dpid)` frame → unpin → overwrite neighbor entries in place (equal width, no slot moves) → FIFO-write via Default context (publishes final + returns frame). Peak = 2 frames transiently + the cid→(page,slot) directory; O(1) in #leaf pages.
